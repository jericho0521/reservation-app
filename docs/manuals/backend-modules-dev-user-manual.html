Tutorials and how-to guides

User guide for owners, staff, and customers

The owner workflow

  1. Open Overview. Confirm the selected tenant and venue, current publication state, reservation activity, conversation state, resources, and channel readiness. If the console shows setup guidance, configure the server-only base URL, service key, tenant, and venue first.
  2. Create or edit the experience. In Studio, select one of eight presets. Complete Profile, Branding, Services, Resources, Availability, Knowledge, and Channels. Presets provide terminology and defaults; they do not create separate backend systems.
  3. Preview before publication. The preview uses the draft with shared customer components. Check business name, colors, terms, services, resource choices, date rules, and channel copy.
  4. Validate. Resolve every reported issue. Publication requires a saved draft, active service, compatible resources where required, operating intervals, and knowledge when conversational channels need it.
  5. Publish. Publication creates an immutable version resolved by the public slug. Later draft edits remain private until the next publication.
  6. Operate. Manage reservations, maintenance, conversations, manual takeover, channels, and analytics from the console.

Expected result

A public slug returns a browser-safe experience. Customers can see services and current availability, create a reservation, and use an opaque management link without receiving owner credentials.

Services, resources, and availability

Services

What the business sells: simulator sessions, rooms, or appointments. Duration, strategy, status, and capacity influence availability.

Resources

What is assigned or consumed: rigs, rooms, or specialists. Archive unused resources instead of deleting historical reservation relationships.

Operating hours

Weekly intervals and date closures establish when booking is possible. Existing bookings and maintenance further reduce availability.

Reservations and maintenance

Use Reservations to inspect the customer, service, slot, assigned resources, source channel, and status. Reschedule only after checking fresh availability. Cancellation changes the reservation state; it does not erase the audit history. Use Resources to create maintenance windows. A maintained resource must disappear from new offers while the maintenance interval is active.

Conversations and staff takeover

  1. Open Conversations and read the complete cross-channel history.
  2. Switch automation to manual before intervening. Unsupported-message fallback replies are suppressed while staff owns the conversation.
  3. Send the staff response. Do not request payment card data, passwords, or unnecessary personal information in chat.
  4. Resolve the request, then return the conversation to automated only when the assistant can safely continue.

WhatsApp setup and simulation

Simulation is the guaranteed credential-free path and exercises the same booking workflow. Linked-device mode uses Baileys. Start a session, display the pairing QR only inside the authorized setup screen, scan it using the business device, and wait for connected status. The qr_code value must never be copied into logs, tickets, screenshots, or chat messages.

Analytics

Analytics provide bounded operational aggregates: funnel stages, source channel, demand by time, popular slots, and simulation inclusion. They are not financial statements or a general data warehouse. Check the selected date range and whether simulation events are included before drawing conclusions.

What customers experience

Customers open a published slug, choose a service and date, view current slots, enter required contact details, and explicitly confirm. Chat and WhatsApp first create a structured proposal; generated text cannot authorize a database mutation. After booking, the customer receives confirmation and an opaque management link. If another customer claims the slot first, the API returns a safe conflict and the interface must load fresh availability.

Learning-oriented setup

Developer tutorial: zero to a working Docker stack

This tutorial starts the complete local platform, explains every container and environment source, and finishes with a real booking. Follow it from the repository root.

Prerequisites

  • Docker Desktop, Docker Engine with the Compose plugin, or another compatible Docker installation.
  • Git for cloning the repository.
  • At least 4 GB of memory available to Docker and free host ports 4100, 4300, and 4400.

No host .env is required

Do not create a host .env for the supported local stack. The reservation-config container generates the database password, JWT signing secret and role tokens, platform service key, and WhatsApp encryption key once. It stores them in a private named volume and gives each service only its own configuration file. Node.js, pnpm, PowerShell, and a Supabase account are not required for this path.

4. Start the complete stack

docker compose up --build -d
docker compose ps --all

The first build downloads the pinned base images and installs the locked pnpm workspace inside build stages. Startup can take several minutes. A successful status has reservation-config, reservation-migrate, and reservation-seed at Exited (0); database, gateway, API, console, and booking report healthy. PostgREST remains running without a host port.

Do not treat one-shot Exited (0) services as failures

Configuration, migration, and seed containers are jobs. Exited (0) means they completed successfully. Any non-zero exit requires log inspection.

7. Diagnose a failed layer

docker compose ps --all
docker compose logs reservation-config
docker compose logs reservation-db reservation-migrate reservation-seed
docker compose logs reservation-rest reservation-gateway reservation-api
docker compose logs reservation-console reservation-booking

Start with the first service that is unhealthy or exited non-zero. A migration checksum mismatch means an already-applied indexed migration changed; restore that file instead of deleting the ledger or volumes. An occupied port requires stopping the conflicting host process or deliberately changing the Compose port mapping and matching browser-facing configuration.

9. Reset, stop, or destroy intentionally

Replace only deterministic demo records

docker compose run --rm reservation-reset

The operations-profile reset uses only the fixed Compose database identity and replaces records owned by final_demo.

Stop while preserving everything

docker compose down

Database data, generated credentials, and WhatsApp session material remain in named volumes.

Discard all local data and generated credentials

docker compose down
RESERVATION_STACK_DESTROY_CONFIRM=DESTROY_LOCAL_STACK docker compose run --rm reservation-destroy

The destroy service has networking disabled, requires the exact confirmation, and clears only the three Compose-managed volumes. The next startup creates a new credential set, empty database, migrations, and seed.

10. Obtain values for a manual or production-style deployment

These values are not needed by the local Compose tutorial. Use them only when the API, database, console, or booking application is deployed outside this stack.

  1. Supabase URL and keys: open the hosted project's Connect dialog or Settings → API Keys. Use the HTTP project URL, publishable/legacy anon key, and server-only secret/legacy service_role key. For self-hosting, obtain the REST gateway URL and matching API keys from that deployment. Never use a PostgreSQL connection string as RESERVATION_SUPABASE_URL.
  2. Platform service key: generate an independent high-entropy value with node -e "process.stdout.write(require('node:crypto').randomBytes(48).toString('base64url') + '\n')". Store the same value in the API and console server secret stores; never expose it to browser JavaScript.
  3. JWT/JWKS alternative: when an identity provider owns authentication, copy its exact issuer, JWKS URL, and API audience from the provider's OpenID/API registration. Use the real issued claim names for subject, tenant IDs, venue IDs, roles, and scopes. Configure the whole group; a partial group fails startup.
  4. Tenant and venue: use the tenant ID provisioned by the operator or identity provider, then call authenticated GET /v1/venues with that tenant scope. The generated GET /v1/tenants/current contract is not wired by the current standalone dispatcher.
  5. Internal and public API URLs: set RESERVATION_PLATFORM_BASE_URL to the API origin reachable by the server process and RESERVATION_PLATFORM_PUBLIC_BASE_URL to the API origin reachable by customer browsers. Add exact deployed browser origins to CORS.
  6. AI: obtain the base URL, server API key, and exact model ID from the chosen OpenAI-compatible provider account.
  7. WhatsApp: generate and retain a server-side encryption key of at least 16 characters, configure a persistent session directory, start session_qr, and scan the authorized pairing QR. The current provider does not use a separate provider API token.

See Configuration and environment variables for the complete variable-by-variable reference, requirements, secret classification, missing-value behavior, and runtime manifest.

Development stack, not production Supabase

This topology intentionally includes only PostgreSQL, PostgREST, the narrow gateway, and this platform's services. It does not provide Supabase Auth, Storage, Realtime, Studio, Edge Functions, TLS, production backups, monitoring, rate limiting, or incident controls.

Optional API-only contributor mode

For API hot reload without database-backed catalog, Studio, reservation, or operations workflows:

pnpm install --frozen-lockfile
pnpm run dev:memory

Full database-backed host development is an advanced alternative, not the supported zero-configuration path. It requires an already migrated PostgreSQL/Supabase REST target, the environment groups in the configuration reference, and separate pnpm run dev, pnpm run dev:console, and pnpm run dev:booking terminals. The Windows/WSL local:supabase:start helper controls a separately installed self-hosted Supabase checkout; it does not migrate or seed this repository by itself.

Understanding-oriented explanation

Current architecture

Architectural classification

This is a modular monolith in a pnpm monorepo. The console, booking app, API, and database are deployable units. Workspace packages are libraries compiled into those applications, not independent microservices.

Owner console ─────────────┐
Public booking ── UI ─ React ─ SDK ─┼─▶ /v1 API ─▶ application/domain ports ─▶ Supabase adapter ─▶ PostgreSQL
External frontend ─────── SDK ─────┘
Web chat / WhatsApp ─▶ conversation orchestrator ─▶ the same availability and reservation mutation

Three operating planes

Control plane

Studio creates drafts, previews, validates, and publishes immutable experience versions.

Data plane

Public and conversational clients read availability and execute conflict-safe reservations.

Operations plane

Staff manage reservations, maintenance, conversations, channels, and analytics.

Confirmed booking sequence

  1. Resolve the published slug or authenticated tenant/venue scope.
  2. Read current service, schedule, resource, booking, and maintenance data.
  3. Offer only valid slots.
  4. Require explicit confirmation for conversational bookings.
  5. Rebind the exact service, slot, and resource immediately before mutation.
  6. Claim idempotency where required.
  7. Execute the atomic PostgreSQL conflict check and insert.
  8. Return confirmation and a hashed-token-backed management link, or return a typed conflict with fresh availability.

Security boundaries

The booking app uses public routes and never receives owner credentials. The console creates its SDK client inside server-only modules and sends the service key plus tenant and venue context from the server. The API centralizes protected route matching and can validate service credentials or JWT/JWKS principals. Most persistence repositories use the service-role client, so production tenant isolation depends on correct API authorization and repository scoping in addition to database policy.

Conversational architecture

Conversation history persists in PostgreSQL. The prepared, unconfirmed booking state currently uses an in-memory store, which is appropriate for the demonstration but not for multiple API replicas or restart-safe production workflows. Move this state to PostgreSQL or a distributed store before horizontal scaling.

Known architectural debt

  • The API composition and route dispatcher are large central files.
  • WhatsApp-specific and unified conversation tables coexist during the transition to a unified inbox.
  • Some provider-runtime construction used by web chat is exported through the WhatsApp package.
  • Package scopes mix historical @project-play and current @reservation-platform names.
  • No job queue, distributed rate limiter, cache, or production observability layer exists yet.

WhatsApp encryption compatibility

When RESERVATION_WHATSAPP_SESSION_ENCRYPTION_KEY is set, session credential payloads are encrypted with AES-256-GCM before persistence and decrypted during restore. All API replicas that read the same session data need the same value. Rotating it without re-pairing or migrating stored material makes the existing session unreadable. Production should set and protect this key; plaintext mode exists only for compatibility.

Get the values: Docker-first local stack

  1. Run docker compose up --build -d. The configuration job generates local values and writes private service-specific files to the named volume.
  2. Do not extract the secret files for normal use; the console and API are already configured consistently.
  3. Validate without printing secrets using docker compose ps --all, http://localhost:4100/v1/health, and the console/booking URLs.
  4. To discard the complete local identity, stop the stack and use the confirmed destroy command. The next startup generates new values.

Get the values: hosted or self-hosted Supabase

  1. Create or select the project. Record its HTTP API gateway URL, not its postgresql:// database connection string.
  2. For hosted Supabase, open the project Connect dialog or Settings → API Keys. Copy a publishable key into RESERVATION_SUPABASE_ANON_KEY and create or copy a secret key into the server-only RESERVATION_SUPABASE_SERVICE_ROLE_KEY. Older projects can use the anon and service_role values under Legacy API Keys. See Supabase: Understanding API keys for the current key model.
  3. For self-hosting, obtain the anonymous and administrative API keys plus gateway origin from that deployment's API-gateway configuration. They are not the database password.
  4. Put the administrative key only in the API secret store. Never expose it through NEXT_PUBLIC_*, browser JavaScript, screenshots, or logs.
  5. Apply migrations 000001–000020, start the API, and validate health plus a scoped authenticated request.

Get the values: application authentication and scope

For service-key mode, generate a new application credential on a trusted machine:

node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"

Capture the output directly into the deployment secret manager. Configure the same value in the API and console server, then clear it from terminal scrollback where practical. For JWT/JWKS mode, copy the issuer, JWKS URL, and API audience from the identity provider's OpenID/API registration and map the actual tenant, venue, role, and scope claim names issued in access tokens.

The local Compose console already uses tenant final_demo and Apex venue 00000000-0000-4000-8000-000000000101. In another deployment, copy the tenant ID from the tenant record provisioned by the operator (or the authorized tenant claim issued by the identity provider), then use that scope with authenticated GET /v1/venues to select a venue. Do not invent identifiers. Although the generated contract and SDK contain GET /v1/tenants/current, the current standalone dispatcher does not wire that operation.

Get the values: URLs, AI, and WhatsApp

  • URLs and CORS: use the API address visible to each process. Container DNS names are valid for server-to-server calls but not for a customer's browser. Add the exact console and booking browser origins to CORS.
  • AI: create a server-side API key with the selected OpenAI-compatible provider, then copy its documented API base URL and an exact model identifier available to the account. Validate readiness without printing the key.
  • WhatsApp: generate the encryption secret with the same Node command, store it server-side, start a session_qr session, and scan the pairing QR in the authorized console using the business device. The current linked-device mode does not use a provider API token. Local Compose simulation needs no phone credential.

Client behavior

  • Safe reads may retry when configured.
  • Mutations do not retry by default.
  • Mutations with an explicit idempotency key may be retried safely according to client configuration.
  • Timeouts use abort signals.
  • PlatformError preserves the platform error body.
  • Streaming chat returns a ReadableStream<Uint8Array>.

Frontend boundary

Frontend projects may import the SDK, React hooks, UI, and contract types. They must not import reservations-supabase, database migrations, service-role clients, runtime composition, or copied reservation mutation logic.

How-to guide

Deployment and operations

Supported local evaluation stack

The root Compose file starts PostgreSQL 16, the indexed migrator, first-run demo seed, PostgREST, a narrow /rest/v1 gateway, the standalone API, owner console, and public booking app. This is the supported local development and demonstration path.

Start and inspect the local stack

docker compose up --build -d
docker compose ps --all
docker compose logs -f

Only API port 4100, console port 4300, and booking port 4400 bind to 127.0.0.1. PostgreSQL, PostgREST, and the gateway remain internal. Credential generation, migrations, and first-run seed must finish before customer-facing services become ready.

Local credential and data lifecycle

The one-shot configuration service creates random database, JWT, service API, and WhatsApp encryption values in the private reservation-stack-config volume. It does not print them or write a host .env. Ordinary restart and docker compose down preserve those values, database data, and WhatsApp session state.

docker compose run --rm reservation-reset
docker compose down
RESERVATION_STACK_DESTROY_CONFIRM=DESTROY_LOCAL_STACK docker compose run --rm reservation-destroy

Destructive local commands

Reset replaces only the guarded deterministic final-demo records. Destroy requires the exact confirmation and clears the three Compose-managed local volumes. Stop the stack before destroy. Neither command accepts an arbitrary database URL.

Diagnose startup

docker compose ps --all
docker compose logs reservation-config
docker compose logs reservation-db reservation-migrate reservation-seed
docker compose logs reservation-rest reservation-gateway reservation-api
docker compose logs reservation-console reservation-booking

Logs identify the failed layer without printing generated credentials. A changed already-applied migration checksum fails closed; restore the indexed migration file instead of editing the ledger.

Local stack boundary

This Compose topology is intentionally smaller than official Supabase and is not a production self-hosting recipe. It has no Supabase Auth, Storage, Realtime, Studio, Edge Functions, TLS, backup scheduler, production monitoring, or incident controls.

Production and manual deployment remain separate

For production-style deployment, build the API with pnpm run docker:build or the root Dockerfile, provision an external migrated PostgreSQL/Supabase target, inject secrets through the platform secret store, and deploy the console and booking Next.js applications separately. The standalone production API image does not apply migrations on startup and does not seed data.

Production sequence

  1. Provision PostgreSQL/Supabase and a secret store.
  2. Apply indexed migrations 000001 through 000020 in order.
  3. Configure authentication, exact CORS origins, tenant/venue access, AI, and WhatsApp as required.
  4. Deploy API, console, and public booking origins over HTTPS.
  5. Run health, authenticated smoke, hosted E2E probes, and tenant-isolation checks.
  6. Configure logs, metrics, alerts, backups, restore tests, rate limits, dependency response, and incident procedures.

Minimum production operations

  • Terminate TLS at a trusted reverse proxy or platform load balancer; do not expose an unencrypted owner API to the internet.
  • Store service-role, owner-authentication, AI, WhatsApp, and encryption secrets in the deployment secret store rather than the image or repository.
  • Back up the database and any required WhatsApp session material, then perform and document restore tests.
  • Collect structured logs without pairing qr_code values, credentials, raw tokens, or unnecessary customer data.
  • Monitor health, latency, error rate, database capacity, provider readiness, certificate expiry, and backup success.
  • Add production-appropriate rate limiting, abuse controls, dependency update response, and incident procedures.

Readiness is environment-specific

/v1/health proves liveness, not complete dependency readiness. WhatsApp readiness separately reports missing provider requirements. pnpm run deploy:verify validates repository configuration and security rules but does not prove an arbitrary host is secure or scalable. Production assurance also needs database policy, backup restoration, monitoring, load, network, secret rotation, and deployed accessibility evidence.

Problem-oriented guide

Troubleshooting

I cannot find a host .env after Docker startup

Likely cause: Nothing is missing. The supported Compose path stores generated credentials in the private reservation-stack-config volume and injects service-specific files.

Resolution: Do not create or extract a host .env. Confirm reservation-config completed with docker compose ps --all, then use the preconfigured applications.

Supabase URL or key is rejected

Likely cause: A PostgreSQL connection string was used as the API URL, the public and administrative keys were swapped, or values came from different projects.

Resolution: Copy the HTTP project API URL and keys from the same deployment. Use the publishable/legacy anon key for RESERVATION_SUPABASE_ANON_KEY and the secret/legacy service_role key only for the server-side service-role variable.

Console is unauthorized even though the API is healthy

Likely cause: The console and API use different RESERVATION_PLATFORM_SERVICE_API_KEY values, or the value was exposed as browser configuration instead of server configuration.

Resolution: Generate one high-entropy application key, store it in both server environments, remove it from all NEXT_PUBLIC_* settings, and restart both applications.

Console tenant or venue is not found

Likely cause: The configured identifiers do not exist together or belong to a different authenticated scope.

Resolution: Compose users should keep final_demo and 00000000-0000-4000-8000-000000000101. Other deployments should copy the operator-provisioned/identity-provider tenant ID, then use it with authenticated GET /v1/venues to select an existing venue. The contract-only GET /v1/tenants/current operation is not wired by the standalone dispatcher.

Booking works server-side but fails in the browser

Likely cause: RESERVATION_PLATFORM_PUBLIC_BASE_URL uses an internal container hostname or the browser origin is absent from CORS.

Resolution: Set the public base URL to the HTTPS/host address customers can reach, and add the exact booking browser origin to RESERVATION_PLATFORM_CORS_ALLOWED_ORIGINS.

WhatsApp session cannot be restored after changing secrets

Likely cause: Stored credentials were encrypted with another RESERVATION_WHATSAPP_SESSION_ENCRYPTION_KEY.

Resolution: Restore the original secret from the deployment secret manager or deliberately clear and re-pair the session. All replicas sharing session data must use the same value.

Docker Compose does not become healthy

Likely cause: A local port is occupied, an image build failed, PostgreSQL is still starting, a migration drift check failed, or a one-shot service exited non-zero.

Resolution: Run docker compose ps --all, then inspect the specific service with docker compose logs SERVICE. Do not delete volumes to hide a migration checksum mismatch.

pnpm install --frozen-lockfile fails

Likely cause: The installed pnpm version differs, the lockfile is stale, or registry access failed.

Resolution: This affects advanced manual development, not the Docker-first path. Run from the repository root, confirm pnpm 10.33.2, inspect the first package-resolution error, and do not delete the lockfile as a first response.

API returns repository not configured

Likely cause: Supabase variables are missing or the reservations module is disabled.

Resolution: In Compose, inspect config, gateway, and API logs. In manual deployments, provide the complete Supabase URL, anonymous key, and service-role key; verify the runtime manifest enables reservations; restart the API.

401 unauthorized or 403 forbidden

Likely cause: Bearer credentials, roles, scopes, or tenant/venue membership do not satisfy the protected route.

Resolution: Check the Authorization header, service-key/JWKS mode, and principal claims. Never solve this by making an owner route public.

Tenant or venue headers are required

Likely cause: The owner request lacks scope.

Resolution: Send X-Reservation-Tenant-Id and X-Reservation-Venue-Id or configure the server-only console client.

Browser request fails CORS

Likely cause: The exact frontend origin is absent from the allowed-origin list.

Resolution: Add the scheme, host, and port to RESERVATION_PLATFORM_CORS_ALLOWED_ORIGINS, restart the API, and repeat the preflight.

Experience cannot publish

Likely cause: Draft, service, resources, operating intervals, knowledge, or channel readiness is incomplete.

Resolution: Open Studio Validation, fix every path-specific issue, save the draft, preview, then publish the current configuration ID.

No slots are returned

Likely cause: The service/date is invalid, hours are closed, resources are unavailable, maintenance overlaps, or existing bookings consume capacity.

Resolution: Inspect service duration/strategy, operating intervals, closures, maintenance, and current bookings for the selected date.

Reservation returns conflict

Likely cause: Availability changed or the idempotency key was reused for a different request.

Resolution: Reload availability. Use a fresh key for a new logical request; reuse an existing key only for the identical retry.

Public slug returns not found

Likely cause: No published configuration exists for the normalized slug.

Resolution: Verify the owner published the experience and that the URL uses lowercase letters, digits, and hyphens.

Chat module disabled or AI unavailable

Likely cause: The optional legacy chat module is not composed, the manifest disables AI, or provider credentials are incomplete.

Resolution: Use deterministic public conversation mode where supported or configure provider base URL, model, and API key consistently with the manifest.

WhatsApp setup or QR is unavailable

Likely cause: The module is disabled, session store is unavailable, the provider is not ready, or no QR is current.

Resolution: Check channel readiness, database configuration, session auth directory, encryption key policy, and session status. Never log the QR payload.

Manual takeover still produces automated replies

Likely cause: The conversation did not enter manual state or the wrong conversation store/path was updated.

Resolution: Refresh the conversation, confirm automation_status is manual, and use the unified staff reply action. Unsupported fallback replies must remain suppressed in manual mode.

Migration index mismatch

Likely cause: Migration files changed without regenerating the checked-in index.

Resolution: Run pnpm run database:migration-index:generate, inspect the diff, then run database:verify-migration-bundle.

E2E reset fails

Likely cause: The database is unreachable, schema is incomplete, or the demo guard rejects the target.

Resolution: Confirm the disposable database, apply all 20 migrations, verify guard variables, then rerun demo:reset and demo:verify.

Hosted probes are skipped

Likely cause: Deployed console or booking URLs were not configured.

Resolution: This is expected locally. Configure the documented hosted URL variables in the deployed verification environment before claiming hosted proof.
