# Remaining Work: Drop-In Package Readiness

## What Is Already Done

- `@project-play/reservations-core` exists as a framework-neutral package.
- `@project-play/reservations-supabase` exists as a Supabase adapter package.
- The current Next.js app imports package boundaries instead of only local
  racing simulator helpers.
- Core examples cover Racing Simulator, PS5 quantity booking, and movie
  ticketing.
- Package build output and type declarations are configured.
- Supabase atomic booking SQL and adapter methods exist for hosts that install
  `create_reservation_atomic(payload jsonb)`.
- Package identity and registry publishing are intentionally deferred; internal
  tarball distribution is documented for external smoke testing.
- Publishing is intentionally blocked by `private: true`.

## What Is Still Left

The code is modular enough for this repository, but not yet fully drop-in for
any app. The remaining work is split into follow-on phases:

1. [Phase 7: Atomic Booking RPC](phase-7-atomic-booking-rpc.md) - implemented
   in source and SQL assets; live database/concurrency verification remains a
   deployment validation task.
2. [Phase 8: Package Identity and Release Workflow](phase-8-package-identity-release-workflow.md)
   - completed as an explicit deferral to internal tarball distribution.
3. [Phase 9: External Consumer Smoke Test](phase-9-external-consumer-smoke-test.md)
   - completed with tarball smoke coverage from a clean consumer.
4. [Phase 10: Plugin Host Contract](phase-10-plugin-host-contract.md)
   - completed as a documentation-only contract. See
     [Plugin Host Contract](plugin-host-contract.md).
5. [Phase 11: Optional Host Service Helpers](phase-11-host-service-helpers.md)
   - proposed follow-up if plain host orchestration helpers are approved.
6. [Phase 12: Optional Framework Adapter Proposals](phase-12-framework-adapter-proposals.md)
   - proposed follow-up if framework-specific route/action adapters are
     approved.

## Main Restrictions Until These Phases Finish

- Supabase booking creation is transaction-safe only after the host database has
  applied `supabase/create-reservation-atomic.sql` or the package SQL asset; the
  SQL was not exercised against a live database in Phase 7.
- Packages are private and cannot be installed from npm or GitHub Packages.
- Package names still use temporary `@project-play/*` identities by explicit
  Phase 8 decision.
- External consumers should use tarballs generated by
  `corepack pnpm run packages:pack`
  until final package names and registry policy are approved.
- A clean external app has installed and smoked the generated tarballs; see
  `external-consumer-smoke-notes.md` and `examples/external-consumer-smoke`.
- The package currently provides domain logic and adapters, not a complete
  embeddable UI widget.
- The plugin host contract is documentation-only. Future host service helpers
  or framework adapters must be separately approved and remain optional.
- Non-Supabase apps need their own repository adapter.

## Change Propagation Rule

If any remaining phase changes package names, public exports, database table
contracts, RPC signatures, release flow, or plugin host contracts, update all
later phase files in this directory before assigning the next subagent.

Every subagent should report:

- Status: `DONE`, `DONE_WITH_CONCERNS`, or `BLOCKED`
- Files changed
- Verification run
- Public API or schema changes
- Downstream phase updates required
