Owner, staff, and customer guide

Run one appointment business

The product model

One Docker installation serves one business. The default installation is blank: it has no demo owner, preset venue, default password, or fixture cookie. The first owner creates a real account in the browser, completes appointment onboarding, and publishes one customer experience.

Before setup

  • Prepare the business name, customer-facing slug, timezone, address, services, durations, practitioners, weekly hours, closures, brand colors, and contact details.
  • Use a unique owner email and a password of at least 12 characters.
  • Optional: prepare an SMTP account, an OpenRouter or other supported BYOK provider credential, and a dedicated WhatsApp account. The web booking channel works without them.
  • Never paste provider keys, setup links, management links, pairing QR values, or customer data into documentation or screenshots.

Owner journey

  1. Create the first owner. Open the one-time /admin/setup?token=… URL supplied by the installer or local setup helper. After acceptance, the token cannot be reused.
  2. Complete onboarding. Configure the appointment business, first location, services, practitioners, operating hours, closures, branding, and channel defaults.
  3. Validate and publish. Resolve every validation issue, preview the experience, and publish. Draft edits remain private until the next publication.
  4. Add business knowledge. In Studio → Knowledge & channels, add FAQs, pasted text, or text-based PDFs. Wait for each source to become ready, then use Test retrieval.
  5. Connect optional providers. Configure AI, email, and WhatsApp in owner settings. These are stored server-side; they do not require editing a host .env.
  6. Run a booking proof. In a private window, choose a service, practitioner, date, and live slot; confirm once; then verify the reservation appears immediately in the console.
  7. Operate daily. Create, reschedule, complete, cancel, or mark appointments no-show; manage practitioners and maintenance; invite staff; handle conversations; and review analytics and system status.

Availability and conflict behavior

Availability is calculated from configured hours and closures, service duration, active practitioner/resource mappings, maintenance, and existing reservations. A slot shown to one customer can be taken before confirmation; the atomic reservation operation then returns a stable conflict and the customer must refresh. Cancelling releases the capacity. Appointment practitioners have capacity one and inactive or unassigned practitioners are excluded.

Knowledge and AI answers

The platform does not send the whole knowledge base to the model. A local multilingual embedding model and PostgreSQL hybrid search select up to five relevant chunks. The configured BYOK model generates the final answer from those chunks and returns customer-safe source labels. Without a provider, deterministic FAQ matching and booking behavior remain available. Retrieval or AI failure must not stop ordinary booking.

Conversations and takeover

Web chat and WhatsApp use the same durable conversation workflow. A proposal is not a reservation until explicitly confirmed through the reservation engine. Switch a conversation to manual before staff replies; automated and unsupported-message fallbacks remain suppressed until automation is resumed.

WhatsApp and email

Production/product mode uses the Baileys linked-device adapter. Start pairing in the authorized console, scan the short-lived QR, and wait for connected status. QR contents are returned only to the UI and are not logged. Persisted credentials are encrypted with the Docker-generated session key. Email requires SMTP settings; a provider API key alone is not an SMTP password unless the provider explicitly documents SMTP credentials.

Customer journey

Customers use the published URL without owner credentials. They select current availability, confirm a reservation, and receive an opaque management link for viewing, rescheduling, or cancelling that booking. The link is a secret capability and must not be published in evidence.

  1. Add an FAQ, pasted policy, or a text-based PDF from Studio → Knowledge & channels.
  2. Respect limits: pasted text 100,000 characters; PDF 5 MiB, 100 pages, and 250,000 extracted characters; up to 100 active sources and 10,000 chunks per venue.
  3. Wait for ready. The worker normalizes text, makes roughly 1,200-character chunks with 200-character overlap, and creates 384-dimensional embeddings locally.
  4. Use Test retrieval. It calls no paid model. Semantic and lexical candidates are fused and at most five chunks / 6,000 characters are returned.
  5. Replace, reindex, or archive a source and confirm stale or archived content is excluded.

RAG flow

The pinned multilingual MiniLM INT8 model is baked into the worker image and runs local-only. PostgreSQL full-text search and pgvector exact cosine search are combined with weighted reciprocal-rank fusion. Only retrieved context reaches the BYOK generation provider. Web chat and WhatsApp share this pipeline and show customer-safe citations.

Step 7 — prove reservation correctness

  1. Open the public URL in a private browser and choose a future slot within configured hours.
  2. Confirm a booking and save the secret management link outside evidence.
  3. Verify it appears immediately in the owner console with the correct local time, practitioner, and web channel.

  5. Reschedule through the management link and verify both customer and owner views.
  6. Cancel and verify capacity becomes available again.
  7. Book the same time with a different available practitioner; it should succeed because practitioner capacity is independent.

Explanation

Current architecture

The platform is a Docker-first modular monolith. Browser applications call a typed /v1 API; application services depend on repository ports; Supabase/PostgreSQL adapters implement persistence; PostgreSQL RPCs enforce atomic availability and reservation rules. A separate worker consumes durable jobs for conversations, notifications, and knowledge indexing.

Customers ──▶ Booking UI ──▶ /v1 API ──▶ application services ──▶ repository ports ──▶ PostgreSQL + pgvector
Owners ─────▶ Console ─────▶ /v1 API              │                                      │
WhatsApp ───▶ Baileys ─────▶ unified conversations │                                      │
                                                  └──▶ durable jobs ──▶ Worker ───────────┘
                                                                          │
Knowledge sources ─▶ normalize/chunk ─▶ local multilingual embeddings ────┘
Retrieved chunks + live booking data ─▶ owner BYOK model ─▶ cited reply

Important boundaries

  • Single business per installation: the product UI creates one business; tenant and venue identifiers remain in storage and contracts for strict scoping and future compatibility.
  • Frontend safety: booking/frontends import only contract types, SDK, React hooks, or UI; database and service-role code stay server-side.
  • Reservation authority: generated text may prepare a proposal, but only the strict reservation operation can create a booking.
  • Availability authority: live database data—not RAG documents—controls prices, services, practitioners, hours, maintenance, and conflicts.
  • Knowledge isolation: every source, chunk, and search is tenant- and venue-scoped; archived sources are excluded immediately.
  • Failure isolation: degraded AI/retrieval must not terminate the API or prevent normal reservations, staff operations, email, or WhatsApp processing.

Hybrid retrieval details

The worker uses the pinned Xenova/paraphrase-multilingual-MiniLM-L12-v2 INT8 ONNX model in local-only mode to make vector(384) embeddings. Query search takes up to 20 cosine candidates at similarity 0.45 or above and 20 lexical candidates, then combines ranks with weighted reciprocal-rank fusion (semantic 0.7, lexical 0.3, rank constant 60). It returns at most five chunks and 6,000 context characters. Exact search is intentional for the expected per-installation corpus.

Security and operations

Setup, session, invitation, password-reset, and customer-management capabilities are single-purpose and stored as hashes where applicable. Provider credentials and WhatsApp material are encrypted at rest using generated installation secrets. QR payloads, document contents, customer queries, raw tokens, and credentials are excluded from ordinary logs. The service-role database client is privileged, so route authorization, tenant/venue validation, repository scoping, RLS, and atomic RPC checks all form the security boundary.

Known scope boundaries

Payments, a marketplace, native mobile apps, multi-business installations, enterprise identity, website crawling, DOCX, OCR, cloud-drive synchronization, and a separate vector database are not part of release 0.2.0.

How-to and reference

SDK, React, UI, and external frontends

Release 0.2.0 ships matching @reservation-platform/sdk and @reservation-platform/contract-types artifacts. Install both from the release bundle/registry; do not use workspace overrides in a consumer project.

Public SDK client

import { createReservationPlatformClient } from "@reservation-platform/sdk";

const client = createReservationPlatformClient({
  baseUrl: "https://appointments.example.com",
});

const experience = await client.getPublicExperience("your-business-slug");
const services = await client.listPublicExperienceServices("your-business-slug");

Authenticated server-only client

import "server-only";
import { createReservationPlatformClient } from "@reservation-platform/sdk";

const client = createReservationPlatformClient({

  getAccessToken: () => process.env.RESERVATION_PLATFORM_SERVICE_API_KEY,

Never put owner credentials in browser code

Owner clients belong in server components, server actions, backend-for-frontend routes, or another trusted server. Public browser clients use public routes and browser-safe configuration only.

Consumer acceptance

  1. Create an empty project outside the monorepo.
  2. Install the matching SDK, contract-types, React, and UI tarballs with no overrides.
  3. Build a frontend that reads the published experience and availability.
  4. Create a real reservation, load it through its management token, reschedule it, and cancel it.
  5. Verify the consumer contains no Supabase, database, backend-runtime, or monorepo-source imports.
  6. Run pnpm run sdk:release-gate, pnpm run sdk:registry-install-proof:strict, and live HTTP/SDK parity proof.

Client behavior

  • Safe reads may retry when configured; mutations do not retry by default.
  • Only an identical logical mutation may reuse its explicit idempotency key.
  • Timeouts use abort signals and PlatformError preserves the stable platform error body.
  • Conversation responses can include customer-safe knowledge citation labels.

Frontend boundary

Frontend projects may import the SDK, React hooks, UI, and contract types. They must not import reservations-supabase, migrations, service-role clients, runtime composition, or copied reservation mutation logic.

Docker deployment and operations

Local product stack

pnpm run stack:up
pnpm run stack:setup-url
pnpm run stack:logs
pnpm run stack:down

The default stack is the blank product, not a demo. Only loopback API 4100, console 4300, and booking 4400 are exposed. PostgreSQL, PostgREST, and the gateway remain internal. Named volumes retain database, configuration identity, and WhatsApp sessions.

Destroy is permanent

pnpm run stack:destroy requires explicit confirmation and deletes product volumes. Demo commands act only on isolated demo volumes. Never destroy a stack to hide a migration or configuration failure.

Production first run

  1. Verify the signed release bundle, checksums, provenance/SBOM, and digest-pinned API, worker, console, booking, and tools images.
  2. Provision the supported Ubuntu host, DNS, ports 80/443, and off-host recovery destination.
  3. Run scripts/production/install.sh with domain, release 0.2.0, and host IP. Do not create a production .env.
  4. Use the one-time browser setup URL; complete seven onboarding steps; publish one business.
  5. Make a real booking and verify it in the console.
  6. Store the recovery key offline; create, checksum, copy, restore, and compare an encrypted backup.
  7. Inspect System Status, health/readiness, worker and migration state, disk/backup status, and a sanitized support bundle.

Operational minimums

  • TLS, restricted ingress, protected Docker host, least-privilege operator access, secret rotation, and no secret-bearing logs.
  • Database and WhatsApp-session backup policy with tested off-host restore.
  • Structured logs, health/readiness, disk/capacity, failed-job visibility, certificate and backup alerts.
  • Tested upgrade/rollback and partial-service recovery procedures.
  • Provider outage behavior: deterministic booking remains usable and degraded components are visible.

Problem-oriented guide

Troubleshooting

The setup link is invalid

Cause: It was already accepted, expired, belongs to another installation identity, or came from an old/destroyed config volume.

Fix: On an incomplete local product installation, run pnpm run stack:setup-url again and use the current link. After first-owner creation, use normal /admin/login; setup cannot be reopened.

I expected demo businesses but the catalog is blank

Cause: Default Compose correctly starts product mode.

Fix: Complete browser onboarding for product acceptance, or stop product mode and explicitly run pnpm run stack:demo:up for Apex, Harbour, and Luma.

Docker Compose does not become healthy

Cause: A port is occupied, a build failed, PostgreSQL is starting, a config/mode guard failed, migration drift exists, or a one-shot service exited non-zero.

Fix: Run docker compose ps --all, then inspect the named service. Product and demo cannot share host ports. Do not delete volumes before understanding the failure.

No booking slots appear

Cause: Closed hours/date, wrong timezone, inactive/unassigned practitioner, missing service/location mapping, maintenance, duration mismatch, or consumed capacity.

Fix: Check Studio validation, IANA timezone, service duration, practitioner mapping, operating intervals, closures, maintenance, and existing reservations. Confirm indexing/AI state is irrelevant to slot calculation.

A displayed slot conflicts at confirmation

Cause: Another customer claimed it after availability loaded.

Fix: This is expected race protection. The UI should show a stable conflict and refresh availability. Reuse an idempotency key only for the identical retry.

The booking is absent from the owner console

Cause: Wrong product/demo stack, tenant/venue/location scope, stale page data, failed mutation, or timezone misunderstanding.

Fix: Confirm the booking response succeeded, refresh the correct installation and location, compare UTC/local time, and inspect API/database logs using the reservation ID—not the management token.

An AI/OpenRouter connection test fails

Cause: Wrong base URL, unavailable model ID, invalid/restricted key, provider credit/policy, or network/TLS failure.

Fix: Copy the exact OpenRouter model identifier and API base URL shown by the provider, test a disposable key, and inspect sanitized system status. Do not paste the key into logs. Deterministic fallback should continue.

A knowledge source stays pending or failed

Cause: Worker unavailable, model assets/checksum failure, unsupported PDF, size limits, duplicate checksum, or indexing retry exhaustion.

Fix: Check reservation-worker and system status; use a text-based unencrypted PDF within limits; select Reindex after resolving the cause. Do not log the document or query.

Retrieval returns no useful match

Cause: Source is not ready, archived, scoped elsewhere, or neither semantic similarity nor lexical terms qualify.

Fix: Use Studio Test retrieval, verify source label/status/scope, and improve approved source wording. No-context answers must offer staff help rather than invent facts.

SMTP connection cannot be established

Cause: API key used instead of SMTP credentials, wrong host/port/TLS, sender/account restriction, or outbound network block.

Fix: Use the provider's documented SMTP host, username, password, port, and TLS mode. For Resend, create/use its SMTP credentials. With SMTP disabled, staff invitation should return a manual invitation link.

WhatsApp QR pairing fails

Cause: Provider unavailable, conflicting pairing, timeout, expired/logged-out session, worker/API/store issue, or product/demo mismatch.

Fix: Read the sanitized status/recovery action, log out an obsolete session, start a fresh pairing, and scan promptly. Expected statuses map to 503, 409, or 504; QR contents must never be logged.

WhatsApp cannot restore after secret change

Cause: Credentials were encrypted with a different session key.

Fix: Restore the original protected configuration/recovery material or deliberately clear and re-pair. All replicas need the same key.

Migration index mismatch

Cause: SQL or release metadata changed without regenerating the checksum index.

Fix: Run pnpm run database:migration-index:generate, inspect the diff, then run the bundle and strict live proofs. The current required migration is 000040.

A strict gate skips or fails for missing evidence

Cause: Live database, registry, provider credential, host, DNS, image, backup, or independent acceptance evidence was not supplied.

Fix: Supply the real disposable dependency and rerun. Record unavailable evidence as pending/not proven; never convert a simulation or skip into a pass.
