Reservation Platform Backend

Backend Modules Developer and User Manual

This manual explains how the modular reservation backend is configured, deployed, and operated. It covers the developer workflow for enabling modules and the staff workflow for using WhatsApp automation, knowledge base replies, and manual takeover.

One business per backend Manifest-driven modules Secrets stay in env WhatsApp and in-app chat are separate

Overview

The backend is designed as a one-business-per-backend reservation platform. A backend can enable reservation APIs, backend AI provider infrastructure, and WhatsApp booking automation through a runtime module manifest. The in-app reservation chat is primarily a frontend-owned experience and remains a reserved integration point in this backend manifest. The manifest answers "which modules should this backend run?" while environment variables answer "what secrets and infrastructure should this backend use?"

Module Architecture

For developers

Create a JSON manifest, keep secrets in environment variables, run migrations, start the backend, and use readiness endpoints to verify the channel before exposing it.

For owners and staff

Connect the WhatsApp account by QR, configure business settings, add knowledge base entries, monitor readiness, and take over conversations when a human response is needed.

Install and First Run

Clone the backend repository. Pull the monorepo that contains apps/api, backend packages, Docker files, and docs.
Activate pnpm through Corepack. Use the package manager version pinned by the repository.
Install workspace dependencies. This installs all packages used by the API runtime and module tests.
Create local environment config. Copy .env.example, then add secrets and runtime settings.
Verify and run. Build packages, run deployment checks, then start the backend locally or with Docker.

1. Clone the repository

git clone <repository-url>
cd reservation-app

2. Enable the pinned package manager

corepack enable
corepack prepare pnpm@10.33.2 --activate
corepack pnpm --version

3. Install dependencies

corepack pnpm install

4. Create a local environment file

cp .env.example .env

Fill in Supabase keys, backend auth, and AI credentials. Keep .env local and never commit real secrets.

5. Verify the workspace

corepack pnpm run packages:build
corepack pnpm run deploy:verify
corepack pnpm run database:verify-migration-bundle

6. Run the backend locally

corepack pnpm dev

Check the health endpoint:

curl http://localhost:4100/v1/health

7. Run the backend with Docker Compose

corepack pnpm run docker:compose:up

Compose mounts configs/racing-sim.platform.json into the container, but does not load it by default. To opt in, set this in .env: 

RESERVATION_PLATFORM_CONFIG_PATH=/app/config/platform.json

If that manifest enables AI and WhatsApp automation, also provide AI_AGENT_API_KEY and complete Supabase settings.

Mental Model

The system has four important layers.

Layer Purpose Examples
Manifest Selects enabled backend modules and non-secret model settings. configs/racing-sim.platform.json, RESERVATION_PLATFORM_CONFIG_PATH
Environment Provides secrets, database URLs, auth config, and local dev toggles. AI_AGENT_API_KEY, Supabase keys, service API key
Runtime Loads the manifest, validates dependencies, wires repositories and modules. apps/api/src/runtime.ts
Owner APIs Let staff configure WhatsApp, knowledge, sessions, and manual takeover. /v1/channels/whatsapp/*
Important: customers should not see AI-specific UI or labels. The AI is an internal automation mechanism behind the business WhatsApp channel.

Developer Quick Start

Choose the path that matches what you are trying to prove. Do not use local memory mode as a production shortcut.

Implementation Path

Path A: inspect or develop backend code without WhatsApp

  1. Install dependencies with corepack pnpm install.
  2. Leave RESERVATION_PLATFORM_CONFIG_PATH blank.
  3. Run corepack pnpm dev.
  4. Confirm GET /v1/health returns status: ok.

Path B: test manifest parsing and module wiring locally

  1. Start from configs/racing-sim.platform.json.
  2. Set a local manifest path.
  3. Provide AI_AGENT_API_KEY if ai.enabled=true.
  4. Use memory store only for local testing if no Supabase config is available.
RESERVATION_PLATFORM_CONFIG_PATH=configs/racing-sim.platform.json

Path C: run the intended Docker backend

  1. Copy .env.example to .env.
  2. Fill Supabase, backend auth, and AI env vars.
  3. Set RESERVATION_PLATFORM_CONFIG_PATH=/app/config/platform.json.
  4. Run corepack pnpm run docker:compose:up.
  5. Confirm health and WhatsApp readiness.
curl http://localhost:4100/v1/health
curl -H "Authorization: Bearer $RESERVATION_PLATFORM_SERVICE_API_KEY" \
  http://localhost:4100/v1/channels/whatsapp/readiness

Path D: prepare production

  1. Apply the package-owned database migrations to the intended Supabase/Postgres project.
  2. Use Supabase/Postgres storage, not memory mode.
  3. Mount a persistent WhatsApp auth directory.
  4. Protect owner routes with service-token or JWT/JWKS auth.
  5. Run readiness before giving customers the WhatsApp number.

Core verification commands before merging

corepack pnpm run deploy:verify
corepack pnpm run database:verify-migration-bundle
corepack pnpm test

Module Manifest

The manifest is strict JSON. It must use version: 1, a non-empty app name, and the supported module keys. Unknown modules fail validation so a typo does not silently disable a feature.

Supported v1 module keys

Module Status Purpose
reservations Supported Reservation catalog, availability, booking, mutation, idempotency, and maintenance APIs.
ai Supported Backend AI provider runtime used by automations such as WhatsApp. This is infrastructure, not the frontend chat UI.
whatsapp Supported Self-hosted linked-device QR WhatsApp channel for one business backend.
inAppChat Reserved Frontend-owned reservation chat experience. The backend manifest keeps this as a future integration point; enabling it currently fails validation.

Example manifest

{
  "version": 1,
  "app": "Racing Sim",
  "modules": {
    "reservations": {
      "enabled": true
    },
    "ai": {
      "enabled": true,
      "provider": "openai-compatible",
      "baseUrl": "https://openrouter.ai/api/v1",
      "model": "openai/gpt-4.1-mini"
    },
    "whatsapp": {
      "enabled": true,
      "provider": "session_qr",
      "automation": {
        "enabled": true,
        "mode": "booking_assistant",
        "staffTakeover": {
          "enabled": true,
          "autoMessageOnTakeover": false
        }
      }
    },
    "inAppChat": {
      "enabled": false
    }
  }
}

Validation rules

  • version must be 1.
  • app must be a non-empty string.
  • Allowed module keys are reservations, ai, whatsapp, and inAppChat.
  • Omitted modules default to disabled.
  • Secret-like keys such as apiKey, secret, token, and password are rejected.
  • whatsapp.automation.enabled=true requires ai.enabled=true.
  • whatsapp.automation.mode=booking_assistant requires reservations.enabled=true.
  • whatsapp.provider must be session_qr. meta_cloud is reserved but not implemented.
  • inAppChat.enabled=true fails in v1 because it is a separate future chatbot runtime.

Environment Variables

Environment variables carry secrets and deployment-specific wiring. Do not put API keys, service-role keys, passwords, private keys, or tokens in the manifest.

Required for Supabase-backed production

RESERVATION_SUPABASE_URL=
RESERVATION_SUPABASE_ANON_KEY=
RESERVATION_SUPABASE_SERVICE_ROLE_KEY=

Choose one backend auth mode

# Simple service-token mode
RESERVATION_PLATFORM_SERVICE_API_KEY=

# Or JWT/JWKS mode
RESERVATION_PLATFORM_AUTH_JWKS_URL=
RESERVATION_PLATFORM_AUTH_ISSUER=
RESERVATION_PLATFORM_AUTH_AUDIENCE=

AI automation secrets

AI_AGENT_API_KEY=

The manifest can set provider, baseUrl, and model. The API key stays in env. If the manifest enables ai, startup requires the API key and a complete provider configuration.

WhatsApp local and production settings

RESERVATION_WHATSAPP_SESSION_AUTH_DIR=/app/.reservation-whatsapp-sessions
RESERVATION_WHATSAPP_SESSION_ENCRYPTION_KEY=
RESERVATION_WHATSAPP_SIMULATION_ENABLED=false
RESERVATION_WHATSAPP_ALLOW_MEMORY_STORE=false
Production warning: memory store is for local dev and tests only. Production should use Supabase/Postgres so sessions, conversations, knowledge, messages, and audit history survive restarts.

Docker Implementation

Docker Compose mounts the example manifest and a persistent WhatsApp auth directory. The manifest is opt-in by default to avoid requiring AI credentials for a plain backend boot.

Default Compose behavior

RESERVATION_PLATFORM_CONFIG_PATH="${RESERVATION_PLATFORM_CONFIG_PATH:-}"

With the default blank value, the backend starts with legacy env-driven module behavior. To load the mounted example manifest, set: 

RESERVATION_PLATFORM_CONFIG_PATH=/app/config/platform.json

Mounted files and volumes

./configs/racing-sim.platform.json:/app/config/platform.json:ro
./data/whatsapp-sessions:/app/.reservation-whatsapp-sessions

Run with Compose

corepack pnpm run docker:compose:up

Stop the container with:

corepack pnpm run docker:compose:down

Database and Migrations

The backend container does not apply migrations at startup. Operators must apply the package-owned Supabase migration bundle intentionally before production traffic. 

corepack pnpm run database:verify-migration-bundle

Production database setup steps

  1. Create or select the Supabase/Postgres project for this one business backend.
  2. Apply the core SQL files under packages/database/migrations/supabase in order.
  3. Confirm the WhatsApp migrations are included if WhatsApp is enabled.
  4. Put the matching Supabase URL, anon key, and service-role key in backend env.
  5. Start the backend and verify readiness before taking traffic.

The repository currently verifies the migration bundle and metadata. Applying SQL to a live database is an operator action through the team's approved Supabase CLI, dashboard SQL editor, or deployment migration runner.

WhatsApp requires the business-agent and staff-takeover migrations:

  • packages/database/migrations/supabase/000012_whatsapp_business_agent.sql
  • packages/database/migrations/supabase/000013_whatsapp_staff_takeover.sql

These migrations persist WhatsApp session state, business config, knowledge entries, conversations, message audit history, and per-conversation automation status.

WhatsApp Developer Setup

WhatsApp Automation Flow

1. Enable the modules

In the manifest, enable reservations, ai, and whatsapp. For booking automation, keep automation.mode as booking_assistant.

2. Provide AI and database env

Set AI_AGENT_API_KEY and Supabase values. For OpenRouter, the example manifest already uses https://openrouter.ai/api/v1.

3. Start the backend

corepack pnpm dev
# or
corepack pnpm run docker:compose:up

4. Connect WhatsApp

Start a QR session through the owner API, scan the QR code with the business WhatsApp account, then check readiness.

5. Configure knowledge

Add active knowledge entries for opening hours, services, booking rules, pricing, cancellation policy, location, and staff escalation. In v1 the WhatsApp responder can use all active business knowledge.

Staff User Manual

What staff need before using it

Role Needs access to Main responsibility
Owner or manager Backend owner dashboard or authenticated API client. Connect WhatsApp, configure business settings, approve readiness, manage knowledge.
Support staff Conversation dashboard with permission to send staff replies. Monitor conversations, take over when needed, and resume automation after resolving issues.
Developer/operator Server env, deployment logs, database project, and migration process. Keep the backend running, apply migrations, configure secrets, and troubleshoot readiness failures.

Staff should not need direct access to Supabase service-role keys, AI provider API keys, server files, or the module manifest. Those are operator responsibilities.

Daily operating workflow

  1. Open the owner/staff dashboard or API client provided by your frontend.
  2. Check WhatsApp readiness before business hours.
  3. Confirm the WhatsApp session is connected.
  4. Review recent conversations for manual handoffs or unresolved questions.
  5. Keep knowledge entries updated when prices, opening hours, services, or policies change.

Connecting WhatsApp

  1. Start the session from the staff tool.
  2. Display the QR code.
  3. Open WhatsApp on the business phone and link a device.
  4. Scan the QR code.
  5. Wait until status becomes connected.

Maintaining the knowledge base

Knowledge entries should be short, factual, and written as business policy. Good entries include:

  • Opening hours and holiday closures.
  • Available services and default booking duration.
  • Pricing rules and deposits.
  • Cancellation and rescheduling policy.
  • Location, parking, and arrival instructions.
  • Escalation rules for staff help.

How automated replies work

When a customer messages the WhatsApp number, the backend stores the inbound message, checks whether the conversation is automated, gathers active knowledge, and asks the AI agent to produce a business reply. If booking tools are ready, the agent can help with reservation workflows. The customer receives the business reply in WhatsApp.

When staff should take over

  • The customer is angry, confused, or asking for an exception.
  • The AI answer is incomplete or unsafe to continue automatically.
  • The customer asks about payment, refunds, private data, or special arrangements.
  • The booking requires human judgment.

Manual mode behavior

Sending a staff reply switches the conversation to manual. While manual, the AI does not reply to new customer messages. Manual mode stays active until staff explicitly resumes automation.

Resuming automation

Resume only after the customer issue is resolved and it is safe for automation to continue. Set the conversation status back to automated. The next customer message can then receive an automated reply.

What customers see

Customers see normal WhatsApp messages from the business. They should not see labels saying an AI is replying, internal metadata, readiness status, or staff takeover audit events.

Production Readiness Checklist

  • Supabase URL, anon key, and service-role key are configured server-side only.
  • Backend auth is configured through service token or JWT/JWKS.
  • Required migrations have been applied.
  • RESERVATION_PLATFORM_CONFIG_PATH points to the intended manifest.
  • The manifest enables only supported modules.
  • AI_AGENT_API_KEY is set when ai.enabled=true.
  • WhatsApp session auth directory is mounted as persistent storage.
  • Business config includes business name, fallback message, and default service id.
  • Knowledge base entries are active and current.
  • GET /v1/channels/whatsapp/readiness reports production_ready=true.

Troubleshooting

SymptomLikely CauseFix
Backend fails at startup with manifest validation error. Unknown module, unsupported provider, missing AI settings, or secret-like key in JSON. Fix the manifest. Move secrets to env. Keep v1 keys only.
Docker Compose starts without WhatsApp enabled. Manifest loading is opt-in and RESERVATION_PLATFORM_CONFIG_PATH is blank. Set RESERVATION_PLATFORM_CONFIG_PATH=/app/config/platform.json.
Session status is disabled. WhatsApp is not enabled through manifest or legacy env. Enable modules.whatsapp.enabled=true or set RESERVATION_WHATSAPP_ENABLED=true.
Readiness says ai_provider is missing. AI provider settings or AI_AGENT_API_KEY are missing. Set the API key and confirm manifest baseUrl and model.
Readiness says reservation_tools is missing. Reservation repositories are not wired, often because Supabase config is absent or reservations are disabled. Configure Supabase and keep reservations.enabled=true.
Staff reply endpoint returns module disabled. Staff takeover is disabled in the manifest. Set staffTakeover.enabled=true if manual takeover is required.
AI does not reply in an existing conversation. The conversation is in manual mode. Resume automation by setting automation_status to automated.

Adding Modules Later

Future backend modules should follow the same separation of concerns: the manifest selects modules, env carries secrets, runtime wiring owns dependency validation, and owner APIs expose configuration.

Recommended implementation steps

  1. Add the new module key to @reservation-platform/platform-config.
  2. Define strict validation rules and safe defaults.
  3. Reject secret-like manifest fields and keep credentials in env.
  4. Wire the module in apps/api/src/runtime.ts.
  5. Add API routes only for the module's owner/user surface.
  6. Add migrations if the module owns persistent backend data.
  7. Update Docker docs, deployment verifiers, and readiness checks.
  8. Add tests for manifest parsing, runtime wiring, route behavior, and disabled-module behavior.
Design rule: in-app AI chat and WhatsApp automation are separate modules. They may share provider-neutral AI infrastructure, but their configuration, user experience, and conversation state should remain separate.
